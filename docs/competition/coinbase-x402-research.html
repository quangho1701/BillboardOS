The decision

Make the paid booking the center of the product.

Recommended pitch: An advertiser agent buys a specific digital billboard slot through an x402-protected endpoint. BillboardOS holds the scarce inventory, confirms the booking only after payment settlement, plays the approved creative, and produces separate booking and playback receipts.

This is a direct application of the repository's existing quote → hold → payment → booking → playback design. It is more distinctive for BillboardOS than a generic paid-research agent. The repository remains a documentation scaffold; this page specifies an integration rather than claiming one exists.

Buyer value

An advertiser can request the right screen and time, state a maximum budget, and receive evidence of what was bought and what played.

Operator value

A small screen owner can quote and sell inventory, enforce a price floor, prevent double booking, and reconcile payment exceptions.

The protocol

x402 is a payment handshake, not a booking engine.

A resource server answers an unpaid request with HTTP 402 Payment Required and a quote containing the amount, asset, network, recipient, and accepted payment scheme. The client signs an authorization and retries. A facilitator can verify and settle it. HTTP v2 carries these messages in PAYMENT-REQUIRED, PAYMENT-SIGNATURE, and PAYMENT-RESPONSE headers. Integration blueprint

A specific slot, a specific quote, a specific payment.

  1. Quote. Store an immutable snapshot: slot ID, price in atomic units, asset, network, pay-to address, expiry, and version. The pricing service can explain audience and time-of-day factors, while enforcing the operator floor.
  2. Hold. Atomically reserve the slot for one buyer. Create a purchase intent tied to that hold and its quote. A second buyer must fail or choose another slot.
  3. Challenge. Protect POST /api/purchases/:holdId with x402. Derive the payment requirement from the stored quote. The Foundation's HTTP route type supports a request-dependent price function.
  4. Pay and reconcile. The buyer checks the actual 402 quote against its budget and signs through a CDP-managed wallet. Record the payment attempt and settlement evidence against the purchase intent.
  5. Confirm and deliver. Only settled payment for the active intent can create a booking. After creative approval, schedule the screen and emit a separate playback receipt.

Price consistency: audience counts or demand may change between the first request and paid retry. Both requests must resolve to the same immutable quote. Never silently recalculate and charge for a different slot or price.

For the first testnet build, use TypeScript with CdpX402Client({ environment: "development" }) on the buyer and the CDP Facilitator with the x402 HTTP resource server on the seller. The official guides cover a managed wallet, Base Sepolia USDC faucet, payment wrapper, and settlement. Buyer quickstart · Seller quickstart · Dynamic price type.

Correctness and recovery

Payment authorization and settlement are different states.

The default exact authorization flow verifies a signature before work and settles after work. For this hackathon's scarce inventory, consider exact with an upfront payment flow so settlement precedes the booking handler. Precheck the active hold and keep a short-lived purchase intent. If payment succeeds but booking fails, record a paid exception for authorized resolution; upfront payment does not provide an automatic application refund. Coinbase payment-flow guide.

AVAILABLE → HELD → PAYMENT_PENDING → BOOKED → SCHEDULED → PLAYED
                         ↘ PAYMENT_UNKNOWN → REVIEW
BOOKED or SCHEDULED → DELIVERY_FAILED → REVIEW
  • Pending settlement: preserve the original payment and transaction reference; do not request another payment until the original outcome is reconciled.
  • Duplicate request: reuse one logical payment ID and one purchase-intent ID; a retry cannot create a second booking.
  • Wrong terms: reject a mismatch in slot, quote version, amount, asset, network, recipient, or expiry.
  • Late payment: never move a settled payment to a different slot automatically. Open a paid exception.
  • Playback: record device, timestamp, creative hash, and status. A playback receipt is evidence that the device displayed the creative; it is not proof of impressions or sales.

Coinbase documents a settlement_pending outcome where a transaction may still confirm. The x402 payment-identifier extension addresses retry deduplication. Settlement reconciliation · Payment identifier.

The existing data-model note correctly flags that a payment event cannot require a booking ID before confirmation. Link payment events first to a hold or purchase intent, then attach the booking when it exists.

Judge-facing script

Two minutes, one purchase, one exception.

  1. 0–20 seconds: show the screen and available ad slot. An advertiser asks its agent for a campaign under a budget.
  2. 20–45 seconds: agent explains the chosen slot, fixed quote, operator floor, and exclusive hold.
  3. 45–75 seconds: show the actual 402, budget check, signed retry, and settlement reference. Label USDC as Base Sepolia test funds.
  4. 75–100 seconds: booking confirms, approved creative appears, and separate payment and playback receipts are visible.
  5. 100–120 seconds: second buyer attempts the same slot and is blocked, or a pending payment opens a review item without creating another charge.
